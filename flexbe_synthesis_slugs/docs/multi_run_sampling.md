# Issue 5: Multi-run sampling across all reported results

Depends on: [Issue 2](batch_run_harness.md) (batch-run harness).

## Context

Nearly all values in the paper's existing Tables I–IV are single samples
today. This issue re-runs every table cell with `N` samples via the Issue 2
harness, independent of the ordering-specific work in Issues 3/4.

The reported table cells are:

- **Table I** — Coffee, one-hot encoding. Columns `1, 2S, 3S, 2F, 3F, 2SP, 3SP`.
- **Table II** — Coffee, enumerated encoding. Columns `2S, 3S, 2F, 3F, 2SP, 3SP`
  (no `1` — that case is a fully hand-written `.slugsin`, not generated by the
  capability pipeline at all, so it has no encoding choice to begin with).
- **Table III** — Two-Rivers. Columns `2S, 3S, 2F, 3F, 2SP, 3SP`, but here the
  leading digit means **encoding** (`2`=one-hot, `3`=enumerated) rather than
  capability-set complexity — the paper explicitly excludes the hand-written
  baseline ("(1)") from this table since "the results were in line with (2)".
- **Table IV** — Quadcopter (Crazyflie). Columns `1S, 2S, 1F, 2F, 1SP, 2SP`
  (`1`=one-hot/31 capabilities, `2`=enumerated/one 5-bit value; no `3` level —
  quadcopter has no basic/extended capability-set split).

**The leading digit's meaning is example-specific** — for Coffee (and only
Coffee) it's capability-set complexity (`2`=`coffee_capabilities.yaml`
baseline, `3`=`coffee_capabilities_extended.yaml`, adds failure outcomes);
for Two-Rivers and Quadcopter it's encoding itself. Don't assume one universal
numbering scheme when building the config matrix for a new example.

`S`/`F` = System-Goal / Fair-Outcome liveness (the paper's own terms; the
codebase's `SlugsSystemGoalLiveness` was renamed from `SlugsAdversarialLiveness`
to match, bringing code in line with the paper rather than introducing new
terminology). `P` suffix = pending propositions included.

**Real gap this issue should close, not just resample**: Coffee/Two-Rivers
columns are `..S, ..F, ..SP` — `SP` (System-Goal + pending) appears but
`FP` (Fair-Outcome + pending) never does. Today's tables cover
`{S, F, S+P}` per capability set/encoding, not the full
`{S,F} × {with,without pending}` cross product Issue 4's matrix calls for.
**Filling in the missing `FP` cells is itself new data, not just added
sampling to existing cells** — flag this distinctly from the "add N runs to
what already exists" framing when writing this up.

## Tables I–IV → harness config-matrix rows

Per capability set (Coffee `2`=basic, `3`=extended; Two-Rivers/Quadcopter have
no such split), the full cross product is `encoding × liveness × pending` =
`2 × 2 × 2` = 8 rows, of which the paper's current tables only populate 6 (S,
F, SP — no FP). Excludes the hand-written baseline (`1` for Coffee/Two-Rivers)
entirely — no capability/liveness/pending choice applies to it, so it's out
of scope for this issue's matrix (report its existing single value as-is,
unchanged, same as the paper does today).
